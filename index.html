0 Introdução

Este guia nasceu de um projeto real de laboratório caseiro. O objetivo: construir uma stack Elastic Stack 8.17.x completa, segura e resiliente — com zero flags --insecure, zero verification_mode: none, e tudo validado de ponta a ponta.

💡 O que você vai ter ao final

Um laboratório com Elasticsearch + Kibana + Fleet Server em Docker (WSL2), coletando logs e métricas de uma VM Windows 10 (VMware) via Elastic Agent, com Sysmon e PowerShell logados, backups automáticos diários e retenção de disco configurada.

Por que esse lab?

  • Aprender SOC/SIEM na prática com uma das plataformas mais usadas no mercado
  • Treinar detecções contra ataques simulados usando dados reais do seu ambiente
  • Portfólio: um projeto sólido para mostrar em entrevistas de Blue Team
  • Sandbox seguro: testar malwares e ferramentas sem risco para sua máquina principal
⚠️ Regra de ouro

Não pule etapas. A ordem importa. Certificados gerados depois do container subir não valem para dados já persistidos. Snapshots antes de upgrades. Service tokens antes de reiniciar o container. Cada passo tem um porquê — respeite.

1 Arquitetura

Topologia final validada. Cada componente tem sua responsabilidade bem definida:

Windows 11 (host físico) — 192.168.100.13 ├── WSL2 + Docker Desktop │ ├── Elasticsearch 8.17.10 → https://localhost:9200 │ ├── Kibana 8.17.10 → https://localhost:5601 │ └── Fleet Server 8.17.10 → https://172.28.16.1:8220 │ │ │ │ Rede elastic-net (bridge Docker) │ │ └────────────┴────────────────────────────────────── │ │ VMware Default Switch (NAT) │ 172.28.16.1 (gateway da VM) │ ▼ VMware Workstation └── Windows 10 VM (172.28.23.5) └── Elastic Agent 8.17.10 ├── Sysmon (config SwiftOnSecurity) ├── PowerShell logs └── System metrics

Fluxo de dados

  1. VM Windows gera eventos (Sysmon, Winlog, métricas)
  2. Elastic Agent coleta e envia via HTTPS para https://172.28.16.1:8220 (Fleet Server)
  3. Fleet Server valida o agente, recebe a policy e encaminha dados para Elasticsearch
  4. Elasticsearch indexa em data streams (logs-winlog.sysmon_operational-default, etc.)
  5. Kibana visualiza via data views (logs-*, metrics-*)

Decisões de segurança

DecisãoPor quê
CA própria, sem Let's EncryptHome lab não tem DNS público; CA interna dá controle total sobre SANs
Service tokens (não senhas)Escopo limitado, auditáveis, revogáveis sem afetar outros serviços
TLS em todo o tráfegoEvita credential sniffing mesmo em rede isolada
VM em rede NAT (não bridge)Isolamento do malware da LAN real da casa
SLM automáticoBackup sem intervenção humana = backup que acontece

3.3 — Geração da CA e certificados

Vamos criar uma Autoridade Certificadora própria e emitir certificados para o Elasticsearch e Kibana. Isso permite que os serviços confiem um no outro sem depender de CAs públicas.

docker-compose.yml (trecho certs) 
services:
  elastic-certs:
    image: docker.elastic.co/elasticsearch/elasticsearch:${STACK_VERSION}
    container_name: elastic-certs
    volumes:
      - ./certs:/usr/share/elasticsearch/certs
    user: "0"
    entrypoint: >
      bash -c '
        if [ ! -f /usr/share/elasticsearch/certs/ca/ca.p12 ]; then
          /usr/share/elasticsearch/bin/elasticsearch-certutil ca \
            --silent --pem --out /usr/share/elasticsearch/certs/ca/ca.zip
          unzip -o /usr/share/elasticsearch/certs/ca/ca.zip -d /usr/share/elasticsearch/certs/ca/
          openssl pkcs12 -in /usr/share/elasticsearch/certs/ca/ca/ca.p12 \
            -clcerts -nokeys -passin pass: \
            -out /usr/share/elasticsearch/certs/ca/ca.crt
        fi
        if [ ! -f /usr/share/elasticsearch/certs/elasticsearch/elasticsearch.p12 ]; then
          /usr/share/elasticsearch/bin/elasticsearch-certutil cert \
            --silent --pem --ca /usr/share/elasticsearch/certs/ca/ca.p12 \
            --ca-pass "" --pass "" \
            --dns elasticsearch,localhost,fleet-server,dispositivo \
            --ip 127.0.0.1,172.28.16.1,192.168.100.13,172.29.64.1,192.168.100.1,172.29.73.217 \
            --out /usr/share/elasticsearch/certs/elasticsearch/elasticsearch.zip
          unzip -o /usr/share/elasticsearch/certs/elasticsearch/elasticsearch.zip \
            -d /usr/share/elasticsearch/certs/elasticsearch/
        fi
      '
💡 Por que esses IPs nos SANs?

127.0.0.1 = acesso local
172.28.16.1 = gateway da VM VMware (Default Switch)
192.168.100.13 = IP da LAN do host Windows 11
172.29.64.1 = adapter WSL no host
192.168.100.1 = VMnet8 do VMware

4 Certificados TLS — Aprofundamento

Conceitos fundamentais

Um certificado X.509 contém três coisas essenciais:

  • CN (Common Name): identidade principal (ex: elasticsearch)
  • SANs (Subject Alternative Names): lista de DNS e IPs válidos
  • Assinatura da CA: prova que a autoridade certificadora confia nesse certificado

Quando um cliente (Kibana, Agent, browser) se conecta via HTTPS, ele:

  1. Recebe o certificado do servidor
  2. Verifica se a CA que assinou está no seu trust store
  3. Verifica se o hostname/IP usado está nos SANs
💡 Por que verification_mode: none é perigoso

Desligar a verificação TLS é o equivalente digital a fechar os olhos num cruzamento. Em laboratório parece inofensivo, mas cria o hábito errado. No mundo real, isso é CVE waiting to happen (MITM trivial).

Regenerando certificados com novos SANs

Se você precisar adicionar IPs/hosts depois (ex: novo adapter, VPN), não precisa regenerar a CA — apenas o certificado do servidor:

bash 
# Backup do cert atual
cd ~/homelab/elastic/certs/elasticsearch
mv elasticsearch.crt elasticsearch.crt.bak
mv elasticsearch.key elasticsearch.key.bak

# Reemite com novos SANs
cd ~/homelab/elastic
docker run --rm -v "$PWD/certs:/certs" \
  docker.elastic.co/elasticsearch/elasticsearch:${STACK_VERSION} \
  bash -c '/usr/share/elasticsearch/bin/elasticsearch-certutil cert \
    --ca /certs/ca/ca.p12 --ca-pass "" --pass "" \
    --name homelab-server \
    --dns elasticsearch,localhost,fleet-server,dispositivo \
    --ip 127.0.0.1,172.28.16.1,192.168.100.13,172.29.64.1,192.168.100.1,172.29.73.217 \
    --out /certs/elasticsearch/elasticsearch.p12'

# Converte p12 → PEM
cd certs/elasticsearch
openssl pkcs12 -in elasticsearch.p12 -clcerts -nokeys -passin pass: -out elasticsearch.crt
openssl pkcs12 -in elasticsearch.p12 -nocerts -nodes -passin pass: -out elasticsearch.key.pem
openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in elasticsearch.key.pem -out elasticsearch.key
rm -f elasticsearch.key.pem

# Ajusta permissões
cd ~/homelab/elastic
sudo chown -R 1000:0 certs
chmod 644 certs/ca/ca.crt certs/elasticsearch/elasticsearch.crt
chmod 600 certs/elasticsearch/elasticsearch.key

# Reinicia quem usa o cert
docker compose restart elasticsearch kibana
docker restart fleet-server

Validando um certificado

bash 
# Ver SANs do certificado
openssl x509 -in certs/elasticsearch/elasticsearch.crt -noout -text | grep -A1 "Subject Alternative Name"

# Testar conexão TLS com verificação cheia
curl --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" https://localhost:9200
curl --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" https://172.28.16.1:9200

Se ambos retornarem JSON sem erro de certificado, seus SANs estão corretos.

5 Service Tokens (Kibana ↔ Elasticsearch)

O problema das senhas

Antigamente, o Kibana se conectava ao Elasticsearch com ELASTICSEARCH_USERNAME=elastic / ELASTICSEARCH_PASSWORD=.... Isso tem dois problemas:

  • O usuário elastic é superuser — um comprometimento do Kibana = controle total do cluster
  • A senha aparece em variáveis de ambiente, logs e backups

A solução: Service Tokens

São credenciais com escopo limitado — só o que o Kibana precisa, nada mais. Criados via API REST ou CLI.

Criando o token do Kibana

bash 
docker exec elasticsearch bin/elasticsearch-service-tokens create \
  elastic/kibana kibana-homelab

# Saída: SERVICE_TOKEN elastic/kibana/kibana-homelab = AAEAAWVsYXN0aWM...
# Copie o valor após o "="
⚠️ Pegadinha da API REST

A API /_security/service/elastic/kibana/credential/... pode retornar no handler found dependendo da configuração de segurança. O CLI é mais confiável e grava o token em config/service_tokens dentro do container.

Aplicando o token no Kibana

.env 
KIBANA_TOKEN=AAEAAWVsYXN0aWMva2liYW5hL2tpYmFuYS1ob21lbGFiOmZnQ3BUdVRUUkZlWjJRZkI5RDlLSEE
docker-compose.yml (serviço kibana) 
environment:
  # Remova estas duas linhas:
  # - ELASTICSEARCH_USERNAME=elastic
  # - ELASTICSEARCH_PASSWORD=${ELASTIC_PASSWORD}
  # Adicione esta:
  - ELASTICSEARCH_SERVICEACCOUNTTOKEN=${KIBANA_TOKEN}
bash 
docker compose up -d
docker compose logs -f kibana
# Aguarde: "Kibana is now available (v8.17.10)"

Backup dos tokens (crítico para upgrades!)

🔥 Não esqueça!

Tokens criados via CLI ficam dentro do container em config/service_tokens. Se o container for recriado (upgrade, docker compose down), os tokens somem e o Kibana/Fleet perdem acesso. Faça backup antes de qualquer upgrade!

bash 
# Backup
docker cp elasticsearch:/usr/share/elasticsearch/config/service_tokens ./service_tokens.bak

# Restore (depois de um upgrade)
docker cp ./service_tokens.bak elasticsearch:/usr/share/elasticsearch/config/service_tokens
docker exec -u 0 elasticsearch chown 1000:0 /usr/share/elasticsearch/config/service_tokens
docker exec -u 0 elasticsearch chmod 600 /usr/share/elasticsearch/config/service_tokens
docker restart elasticsearch

6 Fleet Server

O Fleet Server é o hub de comunicação entre o Kibana e os Elastic Agents. Sem ele, você não consegue gerenciar agents centralizadamente — teria que configurar cada um manualmente.

6.1 — Criando a policy no Kibana

  1. Acesse https://localhost:5601 → Management → Fleet
  2. Aba Agent policies → Create agent policy → nome: fleet-server-policy
  3. Dentro da policy → Add integration → busque Fleet Server → adicione
  4. Copie o Policy ID da URL (algo como 5c97089c-293b-42f2-...)

6.2 — Configurando o Output do Fleet

🔥 Passos críticos

O output padrão vem com http://localhost:9200. Isso não funciona no nosso lab porque (1) usamos HTTPS e (2) o container do Fleet precisa usar o hostname Docker elasticsearch.

  1. Fleet → Settings → Outputs → default → Edit
  2. Em Hosts, coloque os dois (o primeiro é para containers, o segundo para agents externos):
yaml 
https://elasticsearch:9200
https://172.28.16.1:9200

Em Advanced YAML, adicione:

yaml 
ssl.certificate_authorities: ["/certs/ca/ca.crt"]

6.3 — Token do Fleet Server

bash 
docker exec elasticsearch bin/elasticsearch-service-tokens create \
  elastic/fleet-server fleet-homelab
# Copie o token

6.4 — Subindo o Fleet Server

bash 
docker run -d \
  --name fleet-server \
  --network elastic-net \
  -p 8220:8220 \
  -e FLEET_SERVER_ENABLE=true \
  -e FLEET_SERVER_ELASTICSEARCH_HOST=https://elasticsearch:9200 \
  -e FLEET_SERVER_ELASTICSEARCH_CA=/certs/ca/ca.crt \
  -e FLEET_SERVER_SERVICE_TOKEN="COLE_O_TOKEN_AQUI" \
  -e FLEET_SERVER_POLICY_ID="COLE_O_POLICY_ID_AQUI" \
  -e FLEET_URL="https://localhost:8220" \
  -e FLEET_CA=/certs/ca/ca.crt \
  -e FLEET_SERVER_CERT=/certs/elasticsearch/elasticsearch.crt \
  -e FLEET_SERVER_CERT_KEY=/certs/elasticsearch/elasticsearch.key \
  -v "$PWD/certs:/certs:ro" \
  --restart unless-stopped \
  docker.elastic.co/beats/elastic-agent:${STACK_VERSION}
✅ Validação

Acompanhe com docker logs -f fleet-server. Aguarde até ver "state":"HEALTHY". Pode levar 2-3 minutos.

7 Conectividade: WSL2 ↔ VM VMware

O desafio

Temos dois mundos virtualizados que precisam conversar:

  • WSL2 rodando Docker (rede Docker bridge elastic-net)
  • VM VMware rodando Windows 10 (rede Default Switch NAT)

A VM não pode usar localhost para acessar o Fleet Server — localhost dentro da VM é a própria VM. Ela precisa acessar via IP do host Windows 11 que atua como gateway.

Descobrindo os IPs

PowerShell (Windows 11 host) 
ipconfig /all

# Procure por:
# - "vEthernet (Default Switch)" → IP 172.28.x.x (gateway da VM)
# - "vEthernet (WSL)" → IP 172.29.x.x (adapter do WSL)
# - "Ethernet" → IP da LAN (192.168.x.x)
bash (dentro do WSL) 
hostname -I
# Mostra o IP interno do WSL (ex: 172.29.73.217)

Testando a conectividade

De dentro da VM Windows 10 (PowerShell):

PowerShell 
# Testa conectividade TCP
Test-NetConnection 172.28.16.1 -Port 8220
Test-NetConnection 172.28.16.1 -Port 9200

# Deve retornar: TcpTestSucceeded : True
⚠️ Se TcpTestSucceeded : False

Causas comuns:

  • Firewall do Windows 11 bloqueando portas 8220 e 9200
  • Docker Desktop não publicando as portas para a interface correta
  • VM em modo Bridge em vez de NAT

Confiando na CA na VM

Para que o Elastic Agent (e o navegador) confiem no certificado do Fleet Server sem flags de insegurança, precisamos importar a CA no trust store do Windows:

bash (no WSL — exibir CA) 
cat ~/homelab/elastic/certs/ca/ca.crt

Copie o conteúdo (-----BEGIN CERTIFICATE----- até -----END CERTIFICATE-----) e cole em um arquivo C:\elastic\ca.crt na VM.

PowerShell (Admin) na VM 
# Importa a CA como raiz confiável
Import-Certificate -FilePath C:\elastic\ca.crt -CertStoreLocation Cert:\LocalMachine\Root

# Testa que o handshake TLS agora funciona
Invoke-WebRequest -Uri https://172.28.16.1:9200 -UseBasicParsing | Select-Object StatusCode
# Deve retornar StatusCode 401 (TLS OK, só falta credencial)
✅ Por que 401 é bom sinal

Significa que o handshake TLS passou, o certificado foi validado e o servidor respondeu. O 401 é só "me mostre credenciais" — prova que o TLS está funcionando com verificação completa.

8 Elastic Agent no Windows

8.1 — Configurando o Fleet Host no Kibana

  1. Fleet → Settings → Fleet server hosts → Add
  2. Nome: VM Access
  3. URL: https://172.28.16.1:8220

8.2 — Criando a policy do agente

  1. Fleet → Agent policies → Create
  2. Nome: windows-vm
  3. Adicione a integração System (para métricas básicas e logs do SO)

8.3 — Instalando o agente

  1. Fleet → Agents → Add agent
  2. Selecione a policy windows-vm e o Fleet server VM Access
  3. Copie o comando gerado pelo Kibana
PowerShell (Admin) na VM 
# Exemplo do comando que o Kibana gera
$ProgressPreference = 'SilentlyContinue'

8.4 — Validação

No Kibana, Fleet → Agents. Em 1-3 minutos, a VM aparecerá como Healthy. Se ficar em Degraded, verifique:

⚠️ Erro comum: open /certs/ca/ca.crt: The system cannot find the path specified

Significa que o output default aponta para a CA num caminho Linux. Crie o mesmo caminho no Windows:

New-Item -ItemType Directory -Path C:\certs\ca -Force
Copy-Item C:\elastic\ca.crt C:\certs\ca\ca.crt

9 Sysmon + PowerShell Logging

Sysmon é a bíblia do Blue Team no Windows. Registra eventos que o Event Log padrão não captura: criação de processos, conexões de rede, alterações no registro, etc.

9.1 — Instalando Sysmon

PowerShell (Admin) na VM 
cd C:\elastic

# Baixa Sysmon + config comunitária (SwiftOnSecurity)
Invoke-WebRequest -Uri https://download.sysinternals.com/files/Sysmon.zip -OutFile Sysmon.zip
Expand-Archive Sysmon.zip -DestinationPath C:\elastic\sysmon -Force
Invoke-WebRequest -Uri https://raw.githubusercontent.com/SwiftOnSecurity/sysmon-config/master/sysmonconfig-export.xml -OutFile sysmonconfig.xml

# Instala com a config
C:\elastic\sysmon\Sysmon64.exe -accepteula -i C:\elastic\sysmonconfig.xml

9.2 — Validando a instalação

PowerShell 
# Verifica se o canal está ativo
Get-WinEvent -ListLog "Microsoft-Windows-Sysmon/Operational" | Select-Object LogName, IsEnabled, RecordCount

# Lê os últimos eventos
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 3 | Format-List TimeCreated, Id
# Esperado: eventos ID 1 (ProcessCreate), 22 (DNSEvent)
💡 Sobre a config SwiftOnSecurity

É a config mais popular da comunidade. Balanceia visibilidade (captura muita coisa) com ruído (filtra eventos irrelevantes). Mantida pela comunidade e usada em ambientes de produção reais.

9.3 — Habilitando as integrações no Kibana

  1. Fleet → Agent policies → windows-vm → Edit
  2. Add integration → busque Windows → Adicione
  3. Na configuração da integração Windows, habilite os streams:
    • sysmon → ON
    • powershell → ON
    • powershell_operational → ON
  4. Salve e aguarde a policy subir para o agent (rev. 4 ou superior)
⚠️ Não existe "integração Sysmon" para Windows!

A integração "Sysmon" no catálogo é apenas para Linux. No Windows, o Sysmon é lido pela integração Windows via o stream sysmon.

9.4 — Validando a ingestão

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  "https://localhost:9200/_cat/indices/logs-winlog-*,logs-sysmon-*?v&h=index,docs.count"

Esperado: índices logs-winlog.sysmon-default, logs-winlog.powershell.default, etc., com contagem crescente.

10 Upgrade de Versão

🔥 Antes de qualquer upgrade

Faça snapshot (seção 11) e backup dos service tokens (seção 5). O Elasticsearch não pode fazer downgrade. Um upgrade mal-sucedido sem backup = dados perdidos.

10.1 — Backup dos tokens

bash 
docker cp elasticsearch:/usr/share/elasticsearch/config/service_tokens ./service_tokens.bak

10.2 — Atualizar versão no .env

bash 
sed -i 's/^STACK_VERSION=.*/STACK_VERSION=8.17.10/' .env
docker compose pull elasticsearch kibana

10.3 — Recriar containers e restaurar tokens

bash 
# ES primeiro
docker compose up -d elasticsearch
docker cp ./service_tokens.bak elasticsearch:/usr/share/elasticsearch/config/service_tokens
docker exec -u 0 elasticsearch chown 1000:0 /usr/share/elasticsearch/config/service_tokens
docker exec -u 0 elasticsearch chmod 600 /usr/share/elasticsearch/config/service_tokens
docker restart elasticsearch

# Depois Kibana
docker compose up -d kibana

# Por último o Fleet Server (imagem nova)
docker rm -f fleet-server
# Recriar com a nova tag da imagem (seção 6.4)
✅ Validação
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" https://localhost:9200 | grep '"number"'
# Esperado: "number" : "8.17.10"

11 Snapshots e Backup Automático

Um snapshot é um backup completo e consistente do cluster. Permite restaurar o Elasticsearch inteiro em caso de desastre.

11.1 — Configurando o repositório

O diretório backups já foi montado via path.repo no docker-compose. Agora registramos como repositório:

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X PUT "https://localhost:9200/_snapshot/homelab_repo?pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "fs",
    "settings": {
      "location": "/usr/share/elasticsearch/backups",
      "compress": true
    }
  }'

11.2 — Primeiro snapshot manual

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X PUT "https://localhost:9200/_snapshot/homelab_repo/snapshot-$(date +%Y%m%d-%H%M)?wait_for_completion=true&pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "*",
    "ignore_unavailable": true,
    "include_global_state": true
  }'

Aguarde. Esperado: "state" : "SUCCESS".

11.3 — SLM: snapshots automáticos diários

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X PUT "https://localhost:9200/_slm/policy/daily-backup?pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "schedule": "0 30 1 * * ?",
    "name": "<daily-snap-{now/d}>",
    "repository": "homelab_repo",
    "config": {
      "indices": ["*"],
      "ignore_unavailable": true,
      "include_global_state": true
    },
    "retention": {
      "expire_after": "30d",
      "min_count": 5,
      "max_count": 50
    }
  }'
💡 Política de retenção

Backup diário às 01:30. Mantém no mínimo 5 snapshots e no máximo 50. Deleta automaticamente o que passar de 30 dias. Ajuste conforme seu espaço em disco.

11.4 — Teste: executar snapshot agora

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X POST "https://localhost:9200/_slm/policy/daily-backup/_execute?pretty"

# Listar todos os snapshots
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  "https://localhost:9200/_snapshot/homelab_repo/_all?pretty" | grep -E '"(snapshot|state)"'

11.5 — Restaurando um snapshot (emergência)

🔥 Cuidado

Restauro sobrescreve dados. Em produção, teste em cluster separado primeiro.

bash 
# Fechar índices existentes (evita conflito)
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X POST "https://localhost:9200/*-*/_close?pretty"

# Restaurar
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X POST "https://localhost:9200/_snapshot/homelab_repo/NOME_DO_SNAPSHOT/_restore?pretty" \
  -H 'Content-Type: application/json' \
  -d '{"indices": "*", "include_global_state": true}'

12 ILM Customizado (Higiene de Disco)

ILM (Index Lifecycle Management) controla quanto tempo dados ficam e quando rollover acontece. Sem ILM agressivo, logs do Windows e Sysmon vão comer seu disco em semanas.

12.1 — Políticas customizadas

PolicyRetençãoRolloverAplicado em
homelab-logs-short7 dias7d ou 10 GBSysmon, PowerShell, Windows logs
homelab-metrics-short7 dias7d ou 5 GBMétricas system e agent
homelab-logs-agent3 dias3d ou 5 GBLogs internos do Elastic Agent
bash — Criar a policy homelab-logs-short 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X PUT "https://localhost:9200/_ilm/policy/homelab-logs-short?pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "policy": {
      "phases": {
        "hot": {
          "min_age": "0ms",
          "actions": {
            "rollover": { "max_age": "7d", "max_size": "10gb" }
          }
        },
        "delete": {
          "min_age": "7d",
          "actions": { "delete": {} }
        }
      }
    }
  }'

Repita para homelab-metrics-short e homelab-logs-agent ajustando tempos/tamanhos.

12.2 — Index Templates (aplicar as policies)

⚠️ Pegadinha: data_stream: {}

Templates para data streams precisam da chave "data_stream": {}. Sem ela, o Elasticsearch rejeita o template com erro de "no data stream configuration".

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X PUT "https://localhost:9200/_index_template/homelab-logs-windows?pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "index_patterns": ["logs-windows.*-default"],
    "priority": 500,
    "data_stream": {},
    "template": {
      "settings": {
        "index.lifecycle.name": "homelab-logs-short"
      }
    }
  }'

12.3 — Rollover forçado

Índices criados antes do template continuarão com a policy antiga. Force o rollover para aplicar a nova:

bash 
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X POST "https://localhost:9200/logs-windows.sysmon_operational-default/_rollover?pretty"

curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  -X POST "https://localhost:9200/metrics-system.process-default/_rollover?pretty"

12.4 — Validação

bash 
# Ver as policies aplicadas nos índices novos
curl -s --cacert certs/ca/ca.crt -u elastic:"$ELASTIC_PASSWORD" \
  "https://localhost:9200/.ds-*000002/_settings?pretty" | grep -A2 '"lifecycle"'

13 Troubleshooting

🔸 Kibana em loop: ENOENT: no such file or directory, open '/usr/share/elasticsearch/...'

Causa: Caminhos de certificado no compose apontam para o prefixo errado.

Fix: No serviço kibana, todos os caminhos devem começar com /usr/share/kibana/, não /usr/share/elasticsearch/.

🔸 Fleet Server state: DEGRADED com missing config fleet.agent.id

Causa: O Elastic Agent precisa confiar no certificado do próprio Fleet Server para completar o bootstrap.

Fix: Adicione -e FLEET_CA=/certs/ca/ca.crt no docker run do Fleet Server.

🔸 dial tcp [::1]:9200: connection refused

Causa: O agente está tentando conectar ao localhost dentro do próprio container (que não tem ES).

Fix: Verifique FLEET_SERVER_ELASTICSEARCH_HOST — deve ser https://elasticsearch:9200, não localhost.

🔸 Agent Windows Degraded: open /certs/ca/ca.crt: file not found

Causa: O output default usa caminho Linux /certs/ca/ca.crt que não existe no Windows.

Fix: Na VM: New-Item C:\certs\ca -Force; Copy-Item C:\elastic\ca.crt C:\certs\ca\.

🔸 no handler found for uri [/_security/service/...]

Causa: Security desabilitado no Elasticsearch ou API incompatível.

Fix: Use a CLI bin/elasticsearch-service-tokens em vez da API REST.

🔸 composable template would cause data streams to no longer match

Causa: Faltou "data_stream": {} no index template.

Fix: Adicione a chave data_stream vazia no template.

🔸 Service tokens sumiram após upgrade

Causa: Tokens vivem dentro do container em config/service_tokens, não no volume.

Fix: Sempre faça docker cp elasticsearch:/usr/share/elasticsearch/config/service_tokens ./service_tokens.bak antes de upgrades. Restaure com docker cp + chown + chmod 600.
